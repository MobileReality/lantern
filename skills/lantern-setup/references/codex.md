# Codex mapping workflow

Use this route in Codex. Read `authority.md` first. Then use the shared `SKILL.md` sections Language, Feature, Skill files and references, AI files, Sections, Platforms, Areas loop, Hard rules, Procedure, Keeping it true afterwards, and Pull-request records. Skip its Claude Model and Where work is dispatched sections.

Before any semantic mapping write, read the root agent's exact model id from runtime or system metadata and run `node scripts/model.mjs check <that exact id>`. An absent model id is unknown and fails this gate. A copy installed under `.agents/skills` applies the Codex policy by itself; when running these scripts from anywhere else, set `LANTERN_PROVIDER=codex`. `node scripts/model.mjs floor codex` prints which models the policy accepts; do not hard-code a model name, since the policy, not this guide, decides. Map runs Lantern launches are pinned to a model that passes.

The gate covers every write whose content comes from reading or interpreting the project: features and their descriptions, platform rules and labels, map records and primary-language text, relations, notes, and sections. A root agent whose exact id passes the check may write these. Any other or unknown root agent only runs deterministic scripts and delegates every semantic write, including a one-chunk map and final sections, to a native Codex subagent spawned with an explicit model that passes the check (pick the newest one available).

The map records no model, so never write a `#model` line or a `"model"` field. Leave an existing one exactly as it is, even in a file you are editing; only `migrate-model.mjs` removes them, once for the whole map, in its own commit, after the team has updated the skill. Leave records outside your work list as they are. The check above is the only model gate.

If the qualified root has up to two chunks, it may map inline. Otherwise use the available native collaboration spawn tool with an explicit model that passes the check and an appropriate supported reasoning effort; no custom agent name or checked-in profile is required. Before chunk dispatch, a qualified writer creates or updates shared features, systems (only through `systems.mjs add`) and platforms when the shared sections require them. After all chunks, a qualified writer handles applicable sections.

Each chunk brief names the project root, chunk id, primary language, platform, allowed map files, and this installed skill path. Include the instruction: "Apply the Semantic review section of references/codex.md before reporting this chunk complete." Tell the worker to read this Codex guide, `references/format.md`, `references/roles.md`, and the shared Language, Feature, Skill files and references, AI files, Platforms, Hard rules, and Procedure sections; read `.lantern/features` and `.lantern/systems` without editing them; read every todo source file in full; write only assigned map records and matching primary-language keys; and delete from other-language files only keys whose assigned primary text changed. It reports files placed in `other`, uncertain roles, every path changed, and the semantic-review evidence described below. Parallelize only chunks with disjoint map files. The root re-runs the deterministic chunk and partial-validation commands after every result.

## Semantic review

File coverage and a valid hash show that a record exists; they do not show whether it explains the architecture. Before finishing each chunk, review its records against the source while that source is still in context. This applies to inline writers and workers alike. Preserve useful dependency coverage while making the important interactions understandable.

- **Purpose and feature.** State the responsibility in this project, including the distinguishing behavior when adjacent files do similar jobs. Apply an existing feature to files that clearly serve it; leave genuinely shared plumbing untagged. Do not derive these from filenames alone or retag everything to increase counts.
- **Symbols.** For an important call, query, write, render, or type dependency, identify the specific function, component, type or constant in the target. Check both its use in the source and its literal existence in the target before adding `#symbol`. Keep the edge on the file the source directly names. Resolve a local import alias to the target’s exported name only when that name appears literally there. For a barrel with `export *`, retain a file-level barrel edge when no suitable symbol is literal; do not replace it with a transitive edge to a leaf file. A file-level edge is appropriate for a whole-module interaction or an unresolved symbol. Distinct meaningful operations on the same file may have separate symbol edges; avoid duplicate edges that only inflate counts.
- **Relationship labels.** When the target does not explain the interaction, say what flows or why it is used: “persists conversation turns”, “loads tenant membership”, “streamed response blocks”. This is especially useful for generic clients, repositories, shared helpers and multiple operations on the same target. Do not repeat the filename, symbol, arrow, or the word “imports”. Follow format.md's language-key rules; prose belongs in the matching primary-language file.
- **Gotchas.** Explicitly examine non-obvious constraints: authorization exceptions, identity or tenant scope, fallbacks, ordering, side effects, immutable outputs, retries, and names that hide a different behavior. Add a concise note only when the source proves a pitfall that the purpose and relationships do not already explain. Do not invent warnings, restate ordinary behavior, or fill a quota.
- **See also.** Check nearby files or alternate implementations that a reader could plausibly confuse with this one, such as legacy/current handlers or adjacent processors. Use a mapped target and explain when the reader should choose it. Ordinary dependencies already belong in relationships; most files need no see-also pointer.

For example, a handler that calls both `streamBlocks` and `streamTokens` from `reply.ts` can use two `reply.ts#symbol` relationships labelled “response blocks” and “token stream”. If the source explicitly gates one path on a client capability, a gotcha can explain that condition. This is an illustration of evidence-based detail, not an instruction to find these names or conditions in another project.

In the chunk handoff, give one or two source-backed examples of useful semantic detail, with source path and line or symbol. Briefly state which optional fields had no justified candidates. Do not create placeholder notes, extra map fields, or project audit files for this handoff. Structural validation must still pass, but cannot replace this review.

## Completion review

After all chunk workers finish, a qualified writer samples records written by this run, prioritizing complex handlers, orchestration, repositories and AI/tool code where present. Compare the source with the corresponding records: important operations should remain distinguishable, ambiguous flows should be explained, and hidden constraints should not disappear into a generic purpose. Check any worker uncertainty against the source. Inspect the presence of symbols, relationship labels, gotchas and see-also notes across the map; their absence across a substantial application is a reason to review representative records, not a demand for a numeric quota. Assign any supported corrections to exact records and map files for a qualified writer, preserving ownership, then revalidate. Do not weaken validation, fabricate detail, or silently treat structural coverage as semantic review. Report any unresolved quality gaps.

A normal refresh continues to respect the pending-chunk/resume rule. Report gaps in records that were already complete before this run without rewriting them. Revisit those records only for an explicitly requested quality improvement, with exact record/map-file ownership assigned to a qualified writer. Preserve valid relationships and stable feature/platform declarations unless source evidence requires a correction.

The final sections brief names only the section files and matching primary-language files it may write, requires the shared Sections rules and source evidence, and is written by a qualified writer. The root runs settled validation after it returns, `validate.mjs . --settled --require-areas`, and runs step 4a itself before that: a worker never writes `.lantern/areas`.

If no model that passes the check is available, stop without writing mapping output and report that the configured model cannot satisfy the recorded policy.
